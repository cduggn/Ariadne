**Cluster Doctor: model selection and golden-test review — 2026-09-28**

Recommendation: benchmark **Qwen3-30B-A3B-Instruct-2507 in 4-bit on one full A100** as the next conventional-attention baseline, alongside **Qwen3.5-9B BF16** as the efficient modern challenger. Add **Qwen3.6-35B-A3B 4-bit** for the larger hybrid candidate. Repair the evaluation's false positives and false negatives before using it to choose a production model. None of these replacements has been GPU-tested for this repository in this review.

This is a research and design proposal, not an adopted architecture decision. Runtime code, schemas, fixtures, deployment and existing golden results are unchanged. Implementing the proposals below should add the relevant D-n entries and update SPEC in the same changes.

The evidence does not establish a 67% tool-calling ceiling. The saved [fix-check summary](../metrics/golden-fix-check-20260927-221924.summary.json) is **3/5 end-to-end task passes**, including **2/3 easy cases = 66.7%**. [D-39](decisions.md) separately records **9/26 = 34.6%** on the first full pass, and 9/24 before the second pass crashed; its detailed run file was lost. The inherited ~69% result belongs to the trip-planner workload. Tool syntax, successful execution, correct causal diagnosis and useful remediation need separate measurements.

The deployment currently grants a worker **20,480 MiB and 50% GPU cores**, even with just one replica. Scaling down to one replica alone does not give it the whole A100. The 30B 4-bit payload almost consumes the slice's 18 GiB vLLM budget before execution buffers and cache, so it is not a useful replacement at the current slice setting. See [vllm.yaml](../deploy/k8s/vllm.yaml).

The weight estimates above use the published [14B file listing](https://huggingface.co/Qwen/Qwen3-14B-AWQ/tree/main), linked quantizer listings, [9B listing](https://huggingface.co/Qwen/Qwen3.5-9B/tree/main), and Ministral's parameter count. Conversion is decimal GB / 1.073741824. The quantizer's `AWQ` name does not guarantee an `awq` loader: for example, the [30B configuration](https://huggingface.co/cyankiwi/Qwen3-30B-A3B-Instruct-2507-AWQ-4bit/blob/main/config.json) uses compressed-tensors metadata. Let the reviewed checkpoint configuration select its quantization implementation. Pin the exact revision, tokenizer and chat template before any run.

The matrix is intentionally not a numerical ranking across BFCL-v3, BFCL-V4, coding-agent scores and Cluster Doctor. They have different datasets, scaffolds, output budgets and reasoning settings. Published full-precision results also do not certify a community 4-bit checkpoint. There is no evidence here for promising a particular replacement's end-to-end pass rate.

**KV sizing and serving recommendation.** For standard attention:

```text
KV bytes/token = 2 (K,V) × layers × KV heads × head dimension × bytes/element
Qwen3-14B:       2 × 40 × 8 × 128 × 2 = 163,840 bytes = 160 KiB
Qwen3-30B:       2 × 48 × 4 × 128 × 2 =  98,304 bytes =  96 KiB
Qwen3.5-9B:     2 ×  8 × 4 × 256 × 2 =  32,768 bytes =  32 KiB (attention only)
Qwen3.6-35B:    2 × 10 × 2 × 256 × 2 =  20,480 bytes =  20 KiB (attention only)

Illustrative full-GPU conventional-model budget:
  nominal 40 GiB × 0.90 − 4 GiB execution reserve − 16.9 GiB weights
  ≈ 15.1 GiB KV for Qwen3-30B ≈ 165,000 resident KV tokens
```

These calculations use the official [14B config](https://huggingface.co/Qwen/Qwen3-14B-AWQ/blob/main/config.json), [30B Instruct config](https://huggingface.co/Qwen/Qwen3-30B-A3B-Instruct-2507/blob/main/config.json), [Coder config](https://huggingface.co/Qwen/Qwen3-Coder-30B-A3B-Instruct/blob/main/config.json), model-card hybrid layouts, and [Ministral params](https://huggingface.co/mistralai/Ministral-3-14B-Instruct-2512-BF16/blob/main/params.json). Actual device-reported memory, graph capture, quantization workspace, batch settings and fragmentation change the available pool. Use vLLM startup measurements to replace the example. A 24k context consumes 2.25 GiB in the 30B model; a 256k advertised window is not a sensible starting serving limit on this GPU.

For Qwen3.5/3.6, do **not** divide all spare VRAM by the attention-only KV number and call the result capacity. Recurrent-state checkpoints and hybrid allocation must also fit. The [vLLM recipe](https://docs.vllm.ai/projects/recipes/en/latest/Qwen/Qwen3.5.html) flags hybrid `align` prefix caching as experimental; [APC documentation](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/) describes block-boundary restrictions. Verify behavior in the exact pinned version, including cache hits when another tool result is appended. Do not carry the 8B pool size or 0.80 admission threshold over as a measured limit for a new architecture.

Keep the stable tools/rules → inventory card → task → tool-turn ordering and per-run worker affinity. Prefix caching saves repeated **prefill**, not new-token decoding or diagnostic reasoning errors. The observed 95.3% server-wide and 97.7% fix-check prompt-cache shares include growing conversation reuse and repeated fixture traffic; they do not establish that arbitrary new incidents share that much context. Measure cold task starts, distinct tasks sharing a cluster, within-run tool turns and exact task replays separately. Preserve chronological history so later turns extend an existing prefix. Retokenize every model's actual rendered prompt; 3,787 prefix tokens is a Qwen3 measurement, not a universal constant.

Use FP16/BF16 KV for the first quality comparison. Then independently evaluate FP8 KV if the pinned A100 attention backend supports it, with scale calibration and quality checks. It approximately halves attention KV storage; it is not a guarantee of faster decoding and does not halve all hybrid state. A100 supports AWQ/GPTQ/Marlin paths but lacks native FP8 W8A8 compute; some weight-only FP8 paths can still work. The relevant primary references are [vLLM hardware compatibility](https://docs.vllm.ai/en/latest/features/quantization/) and [KV quantization](https://docs.vllm.ai/en/latest/features/quantization/quantized_kvcache/).

Start with one full-GPU worker, no speculative decoding, 24,576 context, `tool_choice=auto`, prefix caching, and low concurrency. Run the current 8B in that topology too, to separate topology from model effects. Keep provider-recommended sampling in explicit model profiles instead of silently applying Qwen3 settings to every family. Retain the current raw tool schemas and restricted-data headers. A later two-worker 14B test is useful for the gateway/course story, after establishing single-worker quality and capacity.

**Golden-test review.** The overall approach is appropriate: injected faults, recorded observations, red herrings, alternative roots and an answer-key-blind runtime validator are valuable. Requiring the cause rather than merely the affected pod is realistic. The largest problems are what the checker currently calls a pass, what evidence it assumes is sufficient, and what information a read-only investigator can actually observe.

Several tests are also too optimistic for the broader goal of debugging application bugs. Most namespaces contain one or two tiny workloads, the prompt enumerates examples resembling the catalogue, and audits reuse the same fixtures. There are few healthy/noisy controls and no recorded live-only GPU faults. There are no representative source-code, database query, request-trace or deployment-diff investigations. With today's tools the honest scope is root causes observable in Kubernetes metadata, allowed logs and approved metrics; arbitrary application bugs may remain unresolved.

Expand coverage through the recorder: multiple object names/topologies per mechanism, same symptom with different causes, repaired counterfactuals, stale warnings, benign historical restarts, unrelated noise, multiple simultaneous causes, partial permissions, expired/unavailable logs, disappearing pods, and injected instructions in tool data. Add unanswerable tasks with an expected abstention. Split development and held-out evaluation by scenario family/variant, and keep held-out examples out of prompt tuning. Do not leak fault IDs, keys or solver hints into reports or the cluster card.

**Runtime validation needs a narrower claim.** This review reproduced acceptance of (a) an explicitly contradictory port explanation and fix, (b) an unrelated existing ref, and (c) duplicate findings, all with the current checker. It also reproduced a `TypeError` for `findings: [null]`. The handwritten schema validator omits several declared type/length/enum/additional-property checks. Strengthen total schema validation and convert malformed submissions into bounded repair outcomes. With the current implementation, “0 ungrounded answers delivered by construction” is not supported.

The evidence ledger also solves live-parity problems: `all_refs` re-reads all container logs and other resources at submission, adding unmetered API calls and observing a different time than the model. Log refs use indices in a moving tail; the same string can refer to different text later. Recorded metric/AWS refs are registered via `backend.dump`, whereas the live backend has no dump. Preserve the external ref format if required, but bind it internally to the original observation and content hash. Live metric/cost citations need the same observed-result path.

A useful architecture improvement is a deterministic initial collection node and a persistent evidence ledger before adaptive investigation, followed by claim validation. Initial collection should expose the same redacted observations the tools expose, as tool turns after the task; it should not put health or expected answers in the cached inventory card. This can save repeated discovery turns and make each model comparison fairer. It changes graph orchestration and requires its own decision, but does not require more agent roles. A reviewer model can be evaluated later; another LLM does not repair a weak evidence contract and adds tokens and latency.

**Benchmark plan once the evaluation is corrected.**

1. Run a small protocol suite using the actual tools: required arguments, singular/plural kinds, booleans, nested findings/affects, invalid calls, recovery, empty results and unavailable data. Record raw-response/parser/schema/execution failures separately. Retain `auto` as the initial control; test constrained decoding independently because D-38 documents a real failure with the old combination.
2. Compare current 8B, 30B Instruct 4-bit and 9B BF16 on the same full-GPU topology. Add 35B hybrid next, then Coder/Ministral/14B as budget permits. Use model-specific parsers/templates and declared sampling. Start non-thinking; test bounded reasoning separately with enough output budget, recording its extra latency and context use.
3. Run all 26 legacy tasks for continuity and the corrected held-out cases, with at least five sampled repetitions per case/profile. Report per-scenario and per-tier rates, paired differences and uncertainty. Repeated seeds measure stability; they do not create new independent fault coverage. Record both first-submission and repaired outcomes.
4. Report: valid-call rate, successful correctly scoped calls, root precision/recall, mechanism/fix correctness, observed citation coverage, healthy false positives, justified abstention, and complete useful diagnoses. Do not replace strict end-to-end correctness with a partial score that hides a harmful fix.
5. For candidates that meet the declared quality target, sweep concurrency 1/4/8/16, increasing only while memory, queue and latency allow. Measure task p50/p95 latency, TTFT, decode rate, cache reuse by cohort, resident cache/state, preemptions, failures, and **correct useful diagnoses per GPU-hour**. Include distinct incident traffic and cold/warm cohorts; exact repeated fixtures alone overstate practical reuse.
6. Select the model on semantic accuracy and useful throughput, then decide whether two smaller workers improve the actual workload. Freeze all tuning before the held-out comparison. GPU execution remains a separate authorized session through `make preflight`, Makefile/`lam`, and guaranteed `make down` cleanup.
