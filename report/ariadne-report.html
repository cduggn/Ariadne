Executive summary

Ariadne is an agent that diagnoses Kubernetes faults by calling read-only tools, and the system around it is a self-hosted inference stack: a Go gateway in front of two vLLM workers that share one H100 through HAMi. Cluster data is restricted, so it never leaves the team's own GPUs. Every number below comes from a committed file in metrics/, and each carries its finding number (F) from design/findings.md.

  • The model is the biggest lever on answers. Qwen3.8-27B diagnoses 86.5% of the golden set [95% CI 74.7–93.3], against 51.9% [38.7–64.9] for Qwen3-8B. It scores 100% on red herrings, the tier where a rule or dashboard points at the wrong object (F1).
  • KV cache is the first limit. One H100 half holds 51,092 tokens of KV, about two full-length (24,576-token) runs. The fit calculator was 34% optimistic for this hybrid model, though within 1% for the standard-attention 8B (F5, F6).
  • The knee is between 8 and 16 concurrent agent runs. With 52 runs per level the pass rate holds at 83–87% up to 8, then falls to 63.5% at 16 and 23.1% at 32 (F24, F40).
  • Sizing admission to KV moves the waiting from vLLM to the gateway. An in-flight cap of 4 per worker cut vLLM preemptions by about 95% on the same node and lowered tail latency about 15%, but finished fewer runs at 16 and 32, because queued requests hit their deadline (F36). Across the full sweep vLLM's own queue never held more than 2 requests (F41).
  • Keeping a run on its worker saves prefill without changing answers. Without stickiness vLLM recomputed 10% more prompt tokens and steps were 8–11% slower, at the same pass rate (F29). The prefix cache serves 87.8% of prompt tokens (F9).
  • Recovery and scaling are measured in minutes. A deleted worker was serving again in 5 min 37 s (F44). KEDA asks for a second worker about a minute after a capacity shed, but a new worker takes 8 min 21 s to load, so scale-down waits 15 quiet minutes (F39, D-51).
  • Two things are unconfirmed. The Mooncake KV hop completed its protocol 53 times with no failures, but nobody has confirmed that the destination pulled the KV rather than recomputing it (F35, F45). vLLM's abort counter didn't move when clients left, so freeing their KV is also unconfirmed (F43).
How the evaluation works. Every measured run replays the golden set: 26 faults recorded from a real Kubernetes cluster, in four tiers (easy, multi-hop, red herring, right-sizing). The model and its tool calls are real and go through the gateway; only the tool answers come from the recordings, so every run sees identical evidence and the pass rates are comparable. The same agent reads a live cluster through a read-only kubectl, but no live-cluster run was measured.

Part 1. Cluster setup

Everything runs on one Lambda Cloud instance with a single H100 80 GB, managed as a one-node k3s cluster. make up takes the first GPU with capacity (GH200, then H100, then A100), and one cloud-init detects the card and deploys the matching topology (F18). HAMi splits the card into two slices so two vLLM workers share it. Prometheus scrapes every component, and Grafana shows three dashboards.

Request path

  1. The agent sends an OpenAI chat completion with its headers. The run id ties the 5 to 16 calls of one diagnosis together.
  2. Guard. Malformed bodies, streaming and client-supplied kv_transfer_params get a 400.
  3. Admit. A tenant over its token quota gets a 429. A request whose worker is below 20% free KV, or that would miss its queue deadline, gets a 503 with its reason (kv_free, timeout_queue) and a Retry-After. Only a 503 may leave the box, and a restricted request never does (fuzz test and alert).
  4. Place. A run stays on the worker that holds its history, unless that worker is much busier or has restarted.
  5. Queue. At most 4 requests run per worker. The rest wait in priority order; batch audits are shed before interactive investigations.
  6. The agent waits out a 429 or 503 (and, since 10-08, a 502 from a worker that went away) for up to about 15 s before the run fails (D-44).

What that means for concurrency

  • About two full-length runs per half. vLLM reports a maximum concurrency of 2.08 at 24,576 tokens, against the fit's 2.9. KV, not the 32-sequence cap, is the first limiter (F6).
  • An agent run is shorter than the maximum on average, but grows. Each run starts at about 4.7k tokens and adds a few hundred per step. Audits reach about 15k tokens.
  • So the gateway allows 4 in flight per worker. D-43 sizes the cap from the measured pool: four runs at the app's length of about 12k tokens, with the shared prefix cached once, need about 36k of the 51k tokens. The earlier cap of 16 was sized for the 8B on an A100 slice and let more work into vLLM than its KV holds (F26).

Part 5. Scaling the worker pool

The vLLM pool is the only pool, and KV per worker is the limit, so KEDA adds workers rather than slots. It scales statefulset/vllm from 1 to 2 workers (the two halves of one H100) on two triggers, both Prometheus recording rules with promtool tests:

  • Demand: workers wanted = ⌈(in flight + queued) ÷ 4⌉, the same cap admission uses, averaged over 2 minutes.
  • Capacity sheds: any capacity refusal (kv_free, queue_full, timeout_queue and the like) adds a worker. A tenant over its quota doesn't count, because that isn't a capacity problem.

Table 9. The autoscaling session (F39). vLLM reported no errors or aborts. The runs lost on one worker ended on gateway refusals (18 in as-up, 16 in as-up2), and with two workers none did. The pass rate follows the worker count, and two workers come back near the 86.5% baseline.

The design consequence. The scaler reacts in about a minute, but a worker takes 8 minutes to load a 27B model and warm up. Scale-down must therefore wait longer than a typical gap between bursts, and the useful signal for scaling up is a capacity shed, not demand alone: under cap 4 the queue drains by shedding, so demand sat at the threshold and the demand trigger never fired (F39). The same pattern was rehearsed on kind first, with no GPU (F38).

Part 6. Validation with agent runs

Each golden task is a fault recorded from a real cluster plus an answer key the agent never sees. The checker is deterministic: nothing is judged by a model. A run passes v2 when the diagnosis names the right root object and category, states the right mechanism, cites only evidence the tools actually showed it during the run, and blames no victim or red herring (D-41).

Where the runs fail

  • Qwen3.8's failures are mostly the audits. Five of its seven failed runs are the three multi-namespace audits: 22 to 24 steps, then inconclusive after the allowed repairs. They run out of steps rather than reasoning wrongly. The other two each passed on their repeat (F3).
  • The 8B lost points to two agent-side defects. The describe tool rejected a capitalised kind 101 times, and diagnoses with more than 8 evidence refs failed validation 24 times, including runs that had found the right cause (F4).
  • Failing closed is a feature. A diagnosis that fails validation gets two repairs, then becomes inconclusive instead of an ungrounded answer (D-24).

At 10× traffic

  • Add workers, not bigger slices: KV per worker is the limit. On one node that means a second card; KEDA's maximum grows with it.
  • Retune the in-flight cap to 6–8 per H100 half, or lengthen the interactive queue deadline (F36).
  • A second gateway replica needs a shared run table, or runs partitioned by id, so stickiness survives.
  • An overflow backend for non-restricted work turns refusals into slower answers.
  • The KV hop pays off once contexts grow, if its transfer is confirmed.
  • Settings that don't fit this workload: the 768-token output cap never bound (F30), and chunked prefill rarely does (F15).
  • Watch power, not utilisation: DCGM's utilisation read 100% at any load, while power rose from about 450 W at up to 8 runs to about 600 W at 16 and 32 (F46).

Appendix. Reproducing the runs

Offline, no GPU

uv sync && make lint test          # Python, Go and the alert rules; CI runs the same
make report                         # rebuild the notebook and figures from metrics/
make matrix                         # regenerate the model matrix (CI fails if stale)
# break a local kind cluster on purpose
make lab-up && make inject FAULTS=oom

A GPU session

make preflight && make up           # lint + tests + fit gate, then the first GPU with capacity
make bringup                        # deploy → scale → measure KV → gateway → dashboards
make tunnel                         # terminal 2: the gateway at localhost:8000
make grafana                        # terminal 3: Grafana at localhost:3000
make check                          # both workers ready through the gateway, KV hop on or off
make bench TAG=q1-h100              # golden set + sweep 1→32 + metrics + probes + export
# the routing A/B's control arm
make gateway POLICY=least_loaded && make bench TAG=q1-h100-ll
git add metrics && git commit       # the node's Prometheus keeps nothing
make down                           # billing stops
